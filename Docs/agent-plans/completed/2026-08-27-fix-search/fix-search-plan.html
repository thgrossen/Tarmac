Overview

The one-way itinerary search only ever queries search.rangeStart, even though the search form already lets a user pick a full departure date range (rangeStart … rangeEnd) and the results table already has a sortable "Date" column built to show multiple departure dates at once. This plan fixes SearchRunner.runOneWay to sweep the whole range, issuing one Ignav one-way request per day and merging the results — mirroring the request-per-candidate, cap-and-sample, dedupe-and-price-sort pattern that RoundTripShapeSearch.swift already uses for round-trip searches.

The work is split into four independently committable milestones: a new user-configurable cap on how many Ignav calls a one-way sweep may make (defaulting to 25, matching round-trip's existing hardcoded cap), the sweep engine itself plus a shared sampling helper, wiring the sweep into SearchRunner together with a new partial-failure indicator on SearchRun, and finally surfacing that partial-failure indicator in RunHistoryView.

Questions & Answers

Should sweeping a one-way date range cap the number of Ignav API calls it makes, like round-trip's shape search already does (RoundTripShapeSearch.defaultCallCap = 25)?
Yes — add a user-configurable preference for the cap, defaulting to 25.
If some days' requests succeed and others fail during the sweep, how should the run report that?
Keep the successful itineraries, but note the partial failure — don't just drop it silently the way round-trip's shape search currently does.

Notes

  • The one-way search form already collects a full range (OneWaySearchForm.swift: "Earliest departure" / "Latest departure" DatePickers feeding SavedSearch.rangeStart/rangeEnd), and RunHistoryView.swift's itinerary table already has a sortable "Date" column for one-way runs. No UI changes are needed to expose the range or display multiple dates — this is a backend-only fix in SearchRunner.swift (plus the new preference and the partial-failure banner from milestones 1 and 4).
  • RoundTripShapeSearch.swift already solves the same shape of problem for round-trip: enumerate candidates, evenly sample down to a cap via sample(_:cap:), fire one request per candidate, dedupe itineraries by ignav_id, sort by price, and track the raw JSON of the cheapest result. Milestone 2 mirrors this for a one-way date sweep rather than departure/return date pairs.
  • Assumption (milestone 2): RoundTripShapeSearch.sample(_:cap:)'s evenly-spaced thinning algorithm will be extracted into a small generic helper shared by both the round-trip candidate sampler and the new one-way date sampler, rather than duplicated. Flag in review if a fully independent one-way implementation is preferred instead.
  • Assumption (milestone 1): the new cap preference is a Stepper ranging 1–100, defaulting to 25, added as its own pane in PreferencesView.swift (label/icon left to implementation, e.g. "Limits" / gauge). Adjust in review if a different range or an existing pane is preferred.
  • SearchRunnerTests.oneWayDispatchesSingleCall currently asserts today's buggy behavior by name ("Dispatches a one-way search to a single call, using the range's earliest date") — milestone 3 must rewrite it, not just extend it, since the fixed behavior is a multi-call sweep.
  • The no-fares message in SearchRunner.swift ("request valid… and billed") confirms Ignav calls cost money per request, which is presumably why round-trip already caps its call count — the same reasoning motivates making the one-way cap explicit and user-configurable rather than hardcoded.
  • SearchRun is a SwiftData @Model; milestone 3 adds a new partialFailureMessage: String? stored property to it. As an optional property with no existing data depending on it, this should be picked up by SwiftData's automatic lightweight migration without a manual migration plan — confirm this holds when implementing.

2. Build the one-way date-range sweep engine

Completed

Completed 2026-08-27

Goal. Add the core logic that turns a one-way SavedSearch's date range into one Ignav request per day (capped and evenly sampled when the range is longer than the cap), aggregates the results, and reports how many day-requests failed — without yet touching SearchRunner or the UI.

Tasks

  • Extract RoundTripShapeSearch.sample(_:cap:)'s evenly-spaced thinning algorithm into a small generic helper (e.g. an Array extension) usable by both round-trip candidates and one-way dates; update RoundTripShapeSearch to call through it. (See the assumption above — confirm this is the preferred approach during review.)
  • Add Tarmac/OneWayDateSweep.swift mirroring RoundTripShapeSearch.swift's structure: a dates(for search: SavedSearch) -> [Date] enumerating every day from min(rangeStart, rangeEnd) to max(rangeStart, rangeEnd) inclusive (UTC calendar, matching RoundTripShapeSearch's existing date handling).
  • Add a result type (e.g. OneWaySweepResult) carrying the aggregated, deduped (by ignav_id), price-sorted itineraries; requestCount (the number of day-requests actually issued, i.e. the sampled/capped count); the raw JSON of the cheapest itinerary found; and enough information for the caller to tell "some days failed" from "all days failed" (e.g. a failedRequestCount alongside requestCount, plus the last error for the all-failed case).
  • Add Tarmac/OneWayDateSweep.run(for:apiKey:cap:defaults:fetch:) async -> OneWaySweepResult, issuing one IgnavClient.oneWay(_:) call per sampled date (via an injectable fetch override for tests, matching RoundTripShapeSearch.run's signature shape) and aggregating as above.
  • Add TarmacTests/OneWayDateSweepTests.swift mirroring RoundTripShapeSearchTests.swift: date enumeration across a range (including a single-day range), cap/sampling behavior on a long range, one request per sampled date with the correct departure_date per request, dedupe-by-ignav_id, price sort, all-days-fail vs. some-days-fail vs. no-days-fail result shape, and (if extracted) the shared sampling helper's own behavior.

Implementation Notes

Implemented via TDD (tests written first, confirmed failing to build against the not-yet-existing symbols, then made to pass). Extracted RoundTripShapeSearch.sample(_:cap:)'s evenly-spaced thinning algorithm into a generic Array.sampled(cap:) extension (Tarmac/Array+Sampling.swift); RoundTripShapeSearch.sample(_:cap:) now delegates to it, keeping its old public signature/doc comment so existing callers and tests are untouched. Added Tarmac/OneWayDateSweep.swift mirroring RoundTripShapeSearch.swift's structure: dates(for:) (UTC calendar, min/max-normalized, end-inclusive), OneWaySweepResult (itineraries, requestCount, failedRequestCount, rawJSON, errorMessage), and run(for:apiKey:cap:defaults:fetch:) issuing one IgnavClient.oneWay(_:) call per sampled date, deduping by ignav_id, price-sorting, and tracking the cheapest raw JSON — matching RoundTripShapeSearch.run's shape. errorMessage is set only when every day fails (itineraries empty); a partial failure instead leaves errorMessage nil with failedRequestCount > 0, giving the future SearchRunner caller (milestone 3) what it needs to distinguish the two cases.

Also marked OneWaySweepPreference.defaultCap as nonisolated (Tarmac/OneWaySweepPreference.swift), needed because OneWayDateSweep.run uses it as a default-parameter value (cap: Int = OneWaySweepPreference.defaultCap) and the project builds with SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor — this is exactly the forward-looking gap milestone 1's automated review flagged (see its Automated Review section), and it surfaced here as expected once the preference was actually used as a default-parameter value.

Added TarmacTests/Array+SamplingTests.swift (generic helper: under-cap, over-cap with exact index sequence, cap-of-one, cap-zero/empty) and TarmacTests/OneWayDateSweepTests.swift mirroring RoundTripShapeSearchTests.swift's conventions: date enumeration (single-day, multi-day, reversed range), one request per sampled date with correct departure_date, cap enforcement, price sort + cheapest-JSON tracking, dedupe by ignav_id, and all three failure shapes (no-fail / partial-fail / all-fail). All 36 relevant tests pass (11 new sweep tests, 4 new sampling-helper tests, plus the pre-existing 15 RoundTripShapeSearchTests unchanged and still green, confirming the extraction didn't regress round-trip). Full app target builds cleanly.

3. Wire the sweep into SearchRunner and track partial failures

Completed

Completed 2026-08-27

Goal. Make SearchRunner.runOneWay actually use the milestone 2 sweep engine instead of a single rangeStart-only request, reading the milestone 1 cap preference, and record when a run's results are incomplete due to some (but not all) day-requests failing.

Tasks

  • Add partialFailureMessage: String? to SearchRun (Tarmac/SearchRun.swift), following the existing optional-property/init pattern used by errorMessage.
  • Rewrite SearchRunner.runOneWay to call OneWayDateSweep.run(for:apiKey:cap: OneWaySweepPreference.currentCap(defaults:),defaults:fetch:) instead of building and sending a single OneWayRequest directly.
  • From the sweep result, set run.requestCount to the actual number of day-requests issued; set run.errorMessage to the existing noFaresMessage/underlying-error handling (mirroring runRoundTrip's result.errorMessage ?? (itineraries.isEmpty ? noFaresMessage : nil)) for the "zero itineraries" case; and set the new run.partialFailureMessage (e.g. "N of M day requests failed.") only when itineraries are non-empty but at least one day-request failed.
  • Update SearchRunner.run's doc comment, which currently states a one-way search "only ever checks search.rangeStart… does not sweep through search.rangeEnd… a possible future improvement" — this is no longer true once this milestone lands.
  • Rewrite SearchRunnerTests.oneWayDispatchesSingleCall (and add new cases) to cover: one request per day across a multi-day range with the correct departure_date per request; requests capped/sampled per the preference when the range exceeds it; run.requestCount matching the actual call count; a partial failure producing a non-nil partialFailureMessage while keeping the successful itineraries; and an all-days-fail run still producing the existing error/no-fares behavior with partialFailureMessage == nil.

Implementation Notes

Implemented via TDD (tests rewritten/added first, confirmed failing against the still-single-request runOneWay, then made to pass). Added partialFailureMessage: String? to SearchRun (Tarmac/SearchRun.swift), following the existing errorMessage optional-property/init pattern. Rewrote SearchRunner.runOneWay (Tarmac/SearchRunner.swift) to call OneWayDateSweep.run(for:apiKey:cap: OneWaySweepPreference.currentCap(defaults:),defaults:fetch:) instead of building a single OneWayRequest; removed the now-unused dateFormatter that only runOneWay had used. Updated SearchRunner.run's doc comment to describe both search kinds sweeping their date range, replacing the stale "only checks rangeStart... future improvement" text.

run.requestCount is set from the sweep's actual issued-call count. The errorMessage/partialFailureMessage decision distinguishes three cases: no failures (existing no-fares/success handling, mirroring runRoundTrip); a partial failure (itineraries non-empty or empty) sets partialFailureMessage ("N of M day requests failed.") and keeps errorMessage friendly rather than the raw underlying error; and a total failure (every sampled day failed) surfaces the underlying error as errorMessage with no partialFailureMessage.

Rewrote oneWayDispatchesSingleCall into oneWaySingleDayRange (single-day range, same rich field-mapping assertions as before) and added oneWaySweepsWholeDateRange (per-day dispatch with correct departure_date), oneWaySweepRespectsCapPreference, oneWayPartialFailureSetsMessage, and oneWayPartialFailureNoItinerariesSurfacesNoFaresMessage. Updated oneWayEmptyResultSurfacesMessage and oneWayFailureSurfacesError for the new 8-day default sweep (makeOneWaySearch()'s Oct 5–12 range) and the sweep's raw-JSON-of-cheapest semantics (rawJSON is now nil, not the single response, when no itinerary is ever found). Gave makeOneWaySearch optional rangeStart/ rangeEnd parameters, mirroring makeRoundTripSearch's existing shape. All other pre-existing one-way tests were re-verified against the new multi-day-sweep default and left unchanged (still valid; several now incidentally rely on dedupe-by-ignav_id across identical daily responses). Full suite and app build pass throughout.

Tasks

  • In RunDetailView (Tarmac/RunHistoryView.swift), add a banner shown when run.partialFailureMessage is set, styled distinctly (e.g. amber/warning) from the existing red errorMessage banner, displayed above the itinerary table so the (still-present) successful itineraries stay visible underneath.
  • Confirm the two banners are mutually exclusive in practice given milestone 3's logic (a run never has both errorMessage and partialFailureMessage set at once) but don't assume it structurally — render each independently based on its own optional.
  • Manually verify in the running app: create/run a one-way search spanning several days and confirm the itinerary table now shows multiple distinct departure dates (via the existing Date column) instead of just one; spot-check the new warning banner by temporarily forcing one day's stubbed oneWayFetch to fail (e.g. via a scratch edit or a SwiftUI preview with a mock SearchRun) since a live partial Ignav failure isn't reproducible on demand.

Implementation Notes

Added a second, independent if let partialFailureMessage = self.run.partialFailureMessage banner to RunDetailView in Tarmac/RunHistoryView.swift, right after the existing red errorMessage banner and before the itineraries/raw-JSON Picker, structurally mirroring the error banner's styling (font, padding, frame, .textSelection(.enabled)) but in amber/orange (.orange foreground, .orange.opacity(0.08) background) to stay visually distinct from the red total-failure banner. Rendered as its own if let, not nested in or coupled to the error banner's condition, so the two are independent per the milestone's requirement.
