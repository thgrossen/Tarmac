Tarmac Backlog Implementation Plan

Generated 2026-08-25 · Source: Docs/agent-plans/active/2026-08-25-tarmac-backlog/tarmac-backlog.html

Overview

This plan implements the ten items in the Tarmac Backlog: a sidebar selection bug, sidebar UI improvements, a new Market preference, a passenger-count field, a faster new-search flow, a cleaner window title, richer and sortable results columns, and an exploratory item on booking links.

The approach groups the work into four phases — Sidebar & Navigation, Search Input & Preferences, Results Table, and Exploration — each containing small, independently reviewable and committable milestones. Preference-style additions (Market) follow the existing AirlinePreference pattern already used for the Airlines preference, for consistency. Two milestones (the sidebar-selection bug and the empty-Duration bug) start with root-cause investigation before any fix, since neither has a confirmed cause yet.

Notes

  • market: "CH" is hardcoded in three places today: SearchViewModel.swift:81, RoundTripShapeSearch.swift:190, and SearchRunner.swift:83. All three need to move onto the new preference.
  • AirlinePreference.swift is the established convention for a UserDefaults-backed search preference (defaults key constants + a current...(defaults:) reader) — the new Market preference should mirror it.
  • SearchViewModel appears to no longer be wired into ContentView (which drives search via SearchRunner and SwiftData @Query instead), but it still owns the apiKeyDefaultsKey constant read elsewhere and still hardcodes market/has no passenger field. Update it for consistency where touched, but its unused search() path is not otherwise in scope.
  • Results-table plumbing runs through SearchRunner.snapshot(for:run:) / legSummary(_:) (SearchRunner.swift) into the SwiftData PriceSnapshot model (PriceSnapshot.swift), rendered by RunHistoryView's itineraryTable — milestones 7–9 all touch this same pipeline.
  • No booking/deep-link field exists anywhere in the current models or client code, so milestone 10 is genuinely exploratory and may conclude with no code change.

Implementation notes
  • Built and ran the app live to reproduce and verify (via xcodebuild with DEVELOPER_DIR pointed at Xcode.app, since xcode-select pointed at the Command Line Tools). Since the terminal process lacked Accessibility/Screen Recording access and the user chose not to grant it, reproduction and verification were done interactively: the user clicked in the running app while a temporary diagnostic .onChange print (with NSUnbufferedIO=YES and stdout redirected to a log file, launching the binary directly rather than via open) and periodic screenshots confirmed exactly what did or didn't happen.
  • Root cause: List(searches, selection: $selection) resolved to SwiftUI's whole-object selection overload (SelectionValue == SavedSearch), which requires SavedSearch: Hashable. SavedSearch is a SwiftData @Model conforming to PersistentModel, whose Hashable/Equatable are based on persistentModelID (a PersistentIdentifier) — but SavedSearch also declares its own id: UUID property, which wins as the witness for Identifiable.id and is what List's internal ForEach uses for row identity. This split identity (UUID for row identity vs. PersistentIdentifier for selection-value equality) silently broke AppKit's row-click→selection-binding path: confirmed live that the setter was never invoked on click, and confirmed via a controlled before/after experiment that switching to ID-based selection fixed it immediately.
  • Fix: SearchSidebar now holds @State private var selectedID: SavedSearch.ID? bound to the List. A guarded onChange(of: selectedID) derives the pre-existing selection: SavedSearch? binding (unchanged from the caller's perspective) by looking it up in searches; a nil selectedID clears selection, but a non-nil selectedID not (yet) found in searches leaves selection untouched rather than clobbering it.
  • That guard exists because of a regression found and fixed during this same milestone: an initial version also synced selectedID from selection (for the NewSearchSheet creation path), creating a two-hop loop that, confirmed live, cleared the selection right after creating a new search (the derived lookup ran before SwiftData's @Query had refreshed to include the new row). Fixed by removing that reverse sync and having NewSearchSheet's onCreate set both selection and selectedID directly (no lookup, no race).
  • No unit tests were added: this is purely declarative SwiftUI/AppKit selection-binding wiring with no unit-testable seam, and the repo has no SwiftUI-interaction test infrastructure (no ViewInspector, no XCUITest target). Verification followed the milestone's own manual-verification steps instead, done live with the user: multiple-row clicks, keyboard arrow-key navigation, and NewSearchSheet auto-selection were each confirmed working after the fix.
  • A global tool hook (from the digidna/imazing plugins) rewrote ContentView.swift's license header to a DigiDNA proprietary notice on every edit, unrelated to this fix. Per user instruction, left as-is for the user to correct manually afterward (the same thing happened and was handled the same way on this plan's predecessor's Milestone 1).
