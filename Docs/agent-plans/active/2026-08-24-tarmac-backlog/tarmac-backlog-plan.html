Tarmac Multi-Search — Implementation Plan

Generated 2026-08-24 · Source Docs/agent-plans/active/2026-08-24-tarmac-backlog/tarmac-backlog.html

Overview

Tarmac is today a single hardcoded search: one form in the sidebar (API key, GVA → LIS, fixed departure/return dates), one round trip call to Ignav, one set of results. This plan turns it into a multi-search app — searches are created and saved from the sidebar, each keeping its own history of refresh runs so price movement over time becomes visible — following tarmac-backlog.html.

The work is sequenced bottom-up: a new SwiftData schema for saved searches and run history first (Phase A), then the Preferences window (Phase B), then the Ignav API client changes the new search types require — a one-way call and a client-side "shape" search for round trips (Phase C) — and only then the sidebar, new-search sheet, and results pane that put it all in front of the user (Phases D–E). Each milestone is sized to be reviewed and committed on its own.

Questions & answers

The round-trip backlog item searches over trip shapes (date range + duration ± flexibility + optional weekend constraint), not a fixed departure/return pair. Ignav's round-trip endpoint only accepts one fixed pair per request — how should the shape search be implemented?

Client-side enumeration: call the existing round-trip endpoint once per candidate date pair implied by the range/duration/flexibility/weekend constraint, and keep the cheapest result. No API changes.

One-way search needs a new Ignav API call that IgnavClient doesn't have today — what's the request/response contract?

Provided directly by the user: POST https://ignav.com/api/fares/one-way with the same field shape as round-trip minus the return date. Full contract in the Appendix.

"Luggage included (soute)" is a new checkbox in both search forms, with no matching field in today's RoundTripRequest — how should it be wired to the API?

UI-only for this plan: captured and stored per saved search, but not sent as a request parameter yet. Flagged as a follow-up backlog item.

Today's hardcoded default search (GVA → LIS, round trip, business, direct-only, LX+TP only) is the app's only search right now. Once the sidebar becomes a list of saved searches, what happens to it?

Seed it as the first saved search on first launch after the upgrade, so the sidebar isn't empty and existing usage carries over.

The backlog's one-way and round-trip option lists don't include an airline restriction, but today's hardcoded search always filters to LX+TP via onlyLXTP/airlines_include. Should the new forms keep that toggle?

Neither drop it nor keep it per-search: add it to the new Preferences window as a global default (initially LX+TP), applied automatically to every search's request instead of being a per-search field.

Notes

  • Key files: Tarmac/ContentView.swift (sidebar + detail UI), Tarmac/SearchViewModel.swift (today's form state, API key storage, and search execution — decomposed across the new sidebar/sheet/results views by this plan), Tarmac/IgnavClient.swift (API client, round-trip only today), Tarmac/models.swift (Ignav request/response DTOs), Tarmac/PriceSnapshot.swift (SwiftData model, redesigned in Milestone 2), Tarmac/TarmacApp.swift (ModelContainer + WindowGroup, gains a Settings scene in Milestone 4).
  • Language: existing UI strings are French ("Clé API", "Trajet", "Chercher", "Recherche…"). Keep new UI text in French for consistency. Superseded during Milestone 4: per user feedback, the app's UI is now English throughout — the existing French strings were translated, and all new UI text in remaining milestones should be English.
  • Billing: Ignav bills per request (per the existing copy, now "request valid… and billed"). This is why Milestone 6 caps how many calls a single round-trip shape search fires per refresh, and surfaces the cap rather than silently truncating.
  • Item.swift is unused default SwiftData template boilerplate, unrelated to this backlog — left untouched.
  • Code style: follow the project's existing conventions throughout — newline before {/}/else, == false over !, isXxx naming for booleans.

Completed 2026-08-24

  • Add a relationship from PriceSnapshot back to its SearchRun (cascade delete), and the inverse itineraries: [PriceSnapshot] on SearchRun.
Implementation notes
  • Added Tarmac/SearchRun.swift: a SearchRun @Model with id, runAt (defaults .now), rawJSON/errorMessage (optional, default nil), requestCount, a savedSearch: SavedSearch? back-reference, and a cascading itineraries: [PriceSnapshot] relationship.

Appendix

Ignav one-way fares contract, as provided for Milestone 5:

curl -X POST "https://ignav.com/api/fares/one-way" \
  -H "X-Api-Key: TA_CLE_API" \
  -H "Content-Type: application/json" \
  -d '{
    "origin": "GVA",
    "destination": "LIS",
    "departure_date": "2026-10-05",
    "cabin_class": "business",
    "max_stops": 0,
    "airlines_include": ["LX", "TP"],
    "market": "CH"
  }'

Additional parameters the endpoint accepts, not used by this plan (see Milestone 5's last task):

ParameterDescription
max_priceStrict maximum price in the market's currency — only itineraries under this threshold are returned.
departure_time_rangeObject with earliest_hour, latest_hour, arrival_earliest_hour, arrival_latest_hour (0–23, local airport time).
min_checked_bags / min_carry_on_bagsMinimum included baggage — the field the "Luggage included" checkbox would eventually map to.
allow_self_transferDefaults to true; set to false to avoid self-transfer (separate ticket) itineraries.
adults, children, infants_in_seat, infants_on_lapPassenger counts, 9 total maximum.
